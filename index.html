别人家的造物：Linger

dek / 摘要

一台开源的本地个人 Agent：12G 显卡上跑 125B 模型、一份每晚自己重写的记忆 wiki、一个会在你睡觉时复盘自己该不该开口的「另一个我」。这二十天它涨了四千颗星，也把一个老问题重新摆上桌面——当算力回到你自己的机器上，一个 agent 产品到底该怎么设计。

约 25 分钟 8 章 · 3 枚小样 读的是 4,028★ 的真实仓库 更新于 2026.11.23

先交代动机：这个系列写到现在，我拆的都是自己的东西——我自己的记忆系统、我自己的沙箱、我自己的驾驶舱。自己写的东西有个毛病，你会不自觉地替它辩护。所以这一篇换个打法：拆一台别人的机器，尽量只用它自己写下来的话，和仓库里能点开看的东西。

挑中的是 simplexai-labs/linger。原因很实在：它想干的事，恰好是我这两年反复在干的事（本地优先、agent 工作台、可回滚的工具执行、长期记忆），但走了一条我完全没有走过的路——把大模型本身塞回本地，然后围绕这件事重新设计产品。看别人怎么解同一道题，比自己再写一遍更能看出自己漏了什么。

全文的事实来源只有三处：仓库 README、`docs/` 下的九篇设计文档、以及 LICENSE 与 release note。文中所有数字都是它们自己写的，我没有复现、没有实机跑过、也不替它们背书；凡是它们标了「模拟测试」的地方，我照抄那个限定词。凡是我自己的判断，都会写成「我认为」。

01

TWO EXTREMES

一台机器，两种极端

Linger 把自己定义成"跑在你自己 PC 上的开源个人 agent"。它同时踩在两个极端上：一个是今天消费级硬件的物理上限，一个是 agent 产品最容易被忽略的那部分——记忆与主动性。

拆解 · 01

仓库 11 月 10 日建，13 天后四千星。它自己的 README 第一句写得很直白："Linger is an open-source personal agent with a Claude-class brain running locally on your PC."（一台跑在你 PC 上、装着 Claude 级大脑的开源个人 agent。）副标题三个词：Open-Source、Local AI、Consumer Macs & PCs。

它的技术栈在 GitHub 上分成两大块：TypeScript 2,200 万字节、Go 1,500 万字节。翻一遍顶层目录就能看出这不是一个 demo 的规模：

表 0 · 顶层目录（取自仓库 main 分支根目录）
目录里面是什么我的读法
apps/desktop、web、computer、teamhub、teamhub-cli、node-services、voice-runtime、linger-installer八个可执行程序，桌面端 / 服务端 / 本机守护进程 / 语音 / 安装器全部拆开
packages/document-files、document-model、knowledge-format、local-installation、service-kit文档与知识格式被抽成独立包，说明「文档」和「wiki」是一等公民

e2e/端到端测试有 e2e，说明它把「桌面 + 本机进程」当成要测的东西

而它真正想解决的问题，用一句话说就是：让"有个 AI 助理替我盯着事"这件事，不再需要订阅一个云端服务。传统做法是你把收件箱、日历、聊天记录交给某家公司的服务器，然后按 token 或按月付钱；Linger 反过来，让这些东西留在你的硬盘上，模型也在你的机器上算。

所以这台机器有两个极端：一头是硬件——要在 12GB 显存的笔记本上跑 125B 参数的模型；另一头是产品——一个会自己开口说话的 agent，它得知道什么时候该说、什么时候该闭嘴。这两头都不容易，而它偏偏把两头顶在了一起。

02

MOE OFFLOAD

12G 上跑 125B：拆开「显存不够」这四个字

这一章是整台机器的地基。也是我最想拆的一段——因为它把一个"不可能"拆成了一道可以算的账。

拆解 · 02

先看它自己给的数字：Qwen3.8-Flash-Next，1250 亿参数，2-bit 量化后文件 39 GB。而它宣称的目标机器是 12 GB 显存 + 64 GB 内存。39 > 12，这是第一直觉上的矛盾。传统做法是"把整个模型装进显存"，装不下就只能换更小的模型——这正是本地 agent 一直做不起来的原因之一：模型一小，能力就掉下来了。

图 1 · 显存不够时的两种放法

A / B COMPARISON

MoE 的关键是：每个 token 只激活全部专家中的少数几个。所以不需要"全部装下"，只需要"装下最可能被选中的那些"。上图右侧的容量与速度数字取自仓库 README 与 docs/local-inference.md 中标注的测试条件；README 同时说明 12GB 档位为模拟测试（用大卡锁显存预算），不是真实 12GB 卡实测。

这套东西叫 PolyStrata

推理引擎单独开源在 simplexai-labs/PolyStrata，C++ 写的，MIT 许可。它的逻辑描述得很朴素：MoE 每生成一个 token 只会用到少数专家，那么就把最常被用到的专家留在 GPU，其次的放在系统内存，Mac 内存不够就落到 SSD，中间按需换入换出。用在硬盘上时还会"预读下一层"。

它公布的成绩是：12 GB RTX 3060 上 45.5 tokens/s；8 GB 笔记本 4070 上 38.1；32 GB 的 5090 上 179。这三档我都照抄了它的限定——前两个数字是模拟档位测的。

我认为这里最值得学的不是"快"，是"分层"这个动作本身。

把"资源不够"从一道是非题，变成了一道"哪些放近、哪些放远"的排序题。这个思路在别的场景一样成立：上下文不够时，哪些事实常驻、哪些落盘；工具太多时，哪些常驻提示词、哪些按需加载。资源永远不够，区别只在于你有没有把它当成排序问题来做。

03

PLANNING

挑模型：一台自动往下筛的五层筛子

"帮我装个模型"听起来是一步，实际是五个决策的组合：哪个模型、哪个量化档、多长上下文、KV 用几位精度、剩下的内存塞什么。

拆解 · 03

docs/local-inference.md 里把这件事叫 Planning：硬件和模型设置一起选，逐层筛，每一层都收窄一次范围，最后剩一个模型、一个量化、一个上下文长度、一个 KV 精度；小模型再往剩下的空里塞。它给了五层：

LAYER 1

平台

Mac / NVIDIA / 其他，决定能用哪套推理路径

LAYER 2

空闲内存

算出语言模型能分到多少，剩下的留给系统

LAYER 3

装得下

权重 + 共享的 128K KV 池都要能放进内存

LAYER 4

质量优先

剩下同样装得下的里面，先挑更聪明的

LAYER 5

塞满剩余

小模型（决策模型、辅助模型）填进剩下的空间

这里有个容易看漏、但我认为很硬的约束：装完不算装好，要回答一个真实问题才算。安装流程里模型是在通过一次真实问答之后才被标记为已安装的。

还有一件事它做了：目录是量出来的，不是抄参数表。它说自己在实验室里跑了 49 个语言模型 × 2 个推理引擎 × IQ1_M 到 Q8_0 的多档量化 × 64K 到 256K 上下文，在 NVIDIA 8–96 GB 和 Mac 16–128 GB 上逐档测。这些数字最终变成安装时给你推荐的那一行。

顺手定了一把尺子

为了回答"这台机器到底能装到多聪明"，它自己定了一个 SimplexAI 评分：38% 编码、19% 研究、19% 专业工作、14% 知识、10% 人类偏好，再扣掉压缩带来的损失。然后它把这个分数放到一个第三方刻度（AIHOT，50 为平均线）上，于是就能写出"12G 档 ≈ Claude Opus 4.6"这样的话。

我对这把尺子的态度是双重的：一方面，给一个混乱的本地模型生态定可比的刻度，这件事本身有价值；另一方面，评分权重是自己定的、刻度是自己贴的，"≈ Opus" 这种类比有多少可信度，取决于你怎么看它的方法论透明度。它至少把权重摊开写了，这比大多数"我们的模型很强"诚实。

04

WIKI & MEMORY

会自己改写的记忆：一份带校验的 wiki

这一章是我读得最久的一章，因为它和我自己那套文件式记忆系统在做同一件事，但答案不一样。

拆解 · 04

Linger 把记忆分成两层：一个关于你工作的个人 wiki（所有 agent 都能搜），每个 agent 对自己对话的记忆。前者是重点。

它的数据结构：一个实体一页

wiki 是一组带类型的 Markdown 页面：客户、联系人、项目、主题各占一页，一个真实世界里的实体一页；每场会议再单独生成一个 Session 页，链接到它涉及的实体。它给的示例图里，Acme 和 Globex 是客户，Dana Lee 和 Sam Park 是联系人，Acme rollout 是项目。

表 1 · 五种页面各自记什么（据 docs/wiki-and-memory.md）
页面它记住的东西
Client 客户他们是谁、怎么合作、需求与约束、未完成与已完成事项、过往联系
Contact 联系人角色、怎么认识的、工作习惯、在意什么、过往联系
Project 项目当前进展、方向决策、未完成与已完成事项
Topic 主题概览，以及你当前的理解
Session 会议一次会：摘要、涉及主题、决策、行动项、你的工作习惯模式

真正有意思的是写入这一侧

大部分"AI 记忆"的做法是：把对话丢给模型，让它输出一份更新后的记忆。Linger 没这么干。它的流程是：模型逐 section 提出修改建议，应用层逐条校验，通过了才落盘。具体规则我抄在这里，因为这几条规则是整章里我最想偷走的部分：

规则 1摘要段要么原样保留，要么改写并给出理由。不允许"顺手润色一下"，因为润色过的摘要无法追溯。
规则 2列表段按条改，每条有应用分配的 ID。本次更新没提到的条目，原样不动。这解决了"重写一遍等于全量覆写"的老问题。
规则 3事实必须引用来源——来自哪条消息、哪个文件版本。改写时必须保留旧文本引用的全部来源，或者明确说明为什么丢掉某条。
规则 4变更日志由程序写，不由模型写。每次改写、编辑、撤回、合并，一条带日期的记录。
规则 5容量是有上限的。摘要段最多 3,000 字符；列表 20 条、每条 500 字符，超出就让模型把最旧的合并成一条带日期的记录。

为什么我觉得这五条比"我们用了 RAG"重要得多？因为记忆系统真正的失败模式不是"记不住"，而是"记住了一个错的、还引用不出来源的东西"。上面五条全都在防这一件事：可保留、可定位、可追溯、可回滚、有边界。这套思路和我自己在做的文件式记忆几乎是同一个方向，但它多了一条我没做到的——变更日志交给程序。让模型写日志，日志本身就是幻觉的入口。

至于效果，它给了一个数字：LoCoMo 长对话记忆基准 95%，声称高于 Zep 94.7%、Mem0 92.5%、Letta 74%、GPT-4o-mini 全上下文 72.9%。这是它自己引用的对比，我没有复核，也不知道它的评测设置。放在这里是因为这个数字至少说明它知道要跟谁比。

05

PROACTIVE & DREAMING

凌晨复盘：一个 agent 怎么学会「什么时候闭嘴」

这是全篇我最喜欢的一段设计。它解决的不是"AI 能不能做事"，而是"AI 该不该现在打扰你"。

拆解 · 05

它把这个角色叫 Another Me（另一个我）。它盯着你的收件箱、日历和 Slack，跟进该跟进的、推进该推进的，只在有事需要你的时候才开口。听着简单，难的是"什么时候算需要你"。

第一层：判断，而不是转发

它给的示例时间线很具体：周一 09:12，Dana Lee 说周五前要报价 → 通用规则判定"还早"，于是它设了个周三 09:00 的提醒；周一 10:40，Slack #random 里有人问午饭 → 判定"不是你的事"，沉默；周一 21:30，站会改到 10:00 → 判定"变了"，立刻告诉你；到了 22:00，免打扰时段开始，23:10 收到一封 newsletter → 只记录，不发送，并在聊天记录里标注 22:00–08:00 不发消息。

第二层：给自己打分，然后改规则

它管这个叫 Dreaming，每晚跑一次。逻辑是这样的：Another Me 白天主动发出的每一条消息，同时也是一个测试样本。夜里 Dreaming 复盘这些消息得到的反应，改写 Another Me 做判断时依据的规则；第二天用新规则判断，当天的反应再喂给下一晚。它明确说了：不做重新训练，学到的东西是一份简短的规则清单。

隐式强化：推两次，就成规则

  • 10/28 你收到提醒「AWS 发票今天到期」，你回：这东西上周就到了，我想早点知道
  • 11/04 又提醒了一次 Figma 的发票，你的反应类似
  • 当晚 Dreaming 把两条同类的线索合成一条：供应商发票 → 立刻告诉我

直接说：一次就够

  • 你回：「等，他们周一就回了？客户回复要立刻告诉我」
  • Dreaming 读出类别（客户回复）和决策（立刻），不需要第二次
  • 你回：「这个点别说了，这类事可以等到我列表里」
  • 它读出类别（会议变更）+ 时间窗（21:00 后）+ 决策（延后）

为什么这套设计我认为值得记一笔？因为它把"主动性"从一句产品口号，拆成了一个有输入、有输出、有反馈回路、而且可解释的机制。大多数 agent 的主动性是"if 某条件 then 通知"，写死在代码里；它的主动性是"规则被观察到的事实改写"，规则还能被人看、被人改。差别在于：前者上线那天就停止成长，后者会跟着你的习惯走形。

同时要说清楚它的风险，它自己也绕不开：这套机制依赖"你的反应"作为信号，而人的反应是被语境污染的。你当天心情不好回了一句"别烦我"，第二天它就学成"这类事别说"。规则清单越短越可控，但也越容易把一次性的情绪学成永久的偏好。我在自己的系统里踩过同类的坑，所以这一章读得格外仔细——它解决的是"怎么学"，没解决"学错了怎么撤"，文档里我没找到规则级别的回滚说明。

小样 2 · NIGHTLY REVIEW（确定性 · 简化模型）

白天信号 0 当前规则 1 今晚该不该开口 —

规则：同类别攒够 2 个同方向信号，就升级成一条规则。

小样 2 同样是我为了讲清机制而写的简化模型，不是 Linger 的实现。真实的 Dreaming 用模型读反馈、归纳线索、写规则，比"计数到二"复杂得多；我这里保留的只有那个骨架：同类信号累积 → 成规则 → 新信号按规则判。要玩真的，去读它的 docs/proactive.md。

06

SHELL & CAGE

壳与笼子：一个单端口、155 条命令、所有动作过闸

前面几章讲的都是"它能做什么"。这一章讲它怎么被管住——我认为这是整台机器里最不显眼、但最能看出工程成熟度的一章。

拆解 · 06

本机不监听任何端口

docs/architecture.md 里画了一张很清楚的图：桌面上的 Computer Daemon 向外拨一个 WebSocket，把消息和文件从服务端取回来，模型调用也走这个通道。文档原话是：本机没有任何东西在网络上监听，本地辅助进程只用 127.0.0.1 或仅属主的 socket。

这个选择的意义在于：一个跑在你电脑上的 agent，最理想的网络姿态是"只出不进"。不需要你配置端口转发、不需要在路由器上开洞、也不需要向别人解释"为什么我电脑上有个服务在跑"。事件先落 SQLite 再发送，断线重连后重放——这是把"网络不可靠"当成默认前提来设计的。

155 条命令，替代一堆 MCP

它做了 teamhub 这个 CLI：TeamHub 自身 56 条（消息、文档、任务、例行、房间、agent、知识、应用、追踪项、档案），加上 99 条 connector（Gmail、Outlook、Teams、Slack、日历、Notion、Drive、OneDrive、Figma、GitLab、表格……）。设计意图是：一个 agent 不需要加载几十个 MCP server，只要认识这一个命令行的 155 个子命令。

几个我认为做对了的细节：

  • 帮助、schema、权限清单从同一份定义生成。不会出现"文档说支持、实际不认"的偏差。
  • 每个 agent 一个 token，48 小时到期，通过 Daemon 那条链路续签。权限是每次调用时由服务端核对身份、成员资格和能力。
  • 写操作带 operation ID。重试返回已存结果；结果未知的报"未知"，而不是重发一次——这是防重复发消息的关键。
  • 文件上传下载 SHA-256 校验，下载不覆盖本地已有文件。
  • 没有 run 也能用。外部 agent 带着自己的 token 也能调。

所有动作过一道闸

桌面操控这块，它用 Cua（macOS / Windows）读窗口元素、点击输入拖拽，用 Playwright 开浏览器（每个 agent 独立 profile，或者直接用你已登录的 Chrome），Shell 跑 agent 自己的命令工具。三者的上游都是同一个东西：Guardrail——先做规则检查，再做一次 LLM 复核，然后才落地执行。

图 4 · 一条动作从被想到到被执行的路径

ACTION PATH

规则先于模型、模型先于执行——这个顺序值得注意：它不是"让模型决定一切"，而是"便宜的规则先拦一道，模型只看剩下的"。

再补两个我认为很聪明的设计：

  • 一条输入通道。屏幕只有一个输入车道，每个 agent 的浏览器各有自己的车道，两个 agent 不会抢同一个屏幕；桌面输入如果需要前台窗口，会等在飞的浏览器调用结束。
  • 每次输入先记日志再执行。结果不确定时，这条车道被阻塞，且这次输入永不重放。这是把"误点一次"的代价压到最低的做法。
07

THE BILL

零 token 是真的，零成本不是

这一章我原本不想写，但它是"本地优先"叙事里最容易被含糊过去的地方，所以必须写清楚。

拆解 · 07

先说它确实做到的部分：本地模型路径上，推理不花钱。文档里写得很明白，聊天、审批、后台的 wiki 与记忆调用，走的都是你机器上那个模型，没有云账单、没有 token 费。这一点是真的，也是它最主要的卖点。

但同一个文档里还写着这些：

表 2 · 哪些环节仍然在网外（据 docs/local-inference.md、docs/architecture.md）

所以准确的说法是：它消除的是"模型推理的 token 费"，不是"所有外部依赖"。这两个差别听起来小，但对一个想"彻底离线"的用户来说很关键——如果你要的是断网可用，那网页搜索、语音、连接应用这三块都得另想办法。

还有一项成本它不说，但躲不掉：硬件。它自己给的门槛是 12GB 显存 + 64GB 内存。它推荐的档位里，Mac 24GB 装的是 27B 的 IQ3_S 量化，12GB 卡上首 token 要等大约 3 分钟。零 token 费换来的是"你的机器在替你付电费和时间"。这笔账值不值，取决于你拿它干什么。

08

TAKEAWAYS

如果是你来做，会先偷哪五条

拆别人机器的终点不是评价，是拿走能用的东西。下面五条是我读完九篇文档之后，真的想搬到自己系统里的。

拆解 · 08
01让"更新"变成"提议 + 校验"，而不是"重写"。模型只输出差异和理由，应用层逐条检查，日志由程序写。这一条可以直接搬进任何有长期状态的系统。
02本机只出不进。一个拨出去的 WebSocket 就能解决端口、防火墙、"我电脑上为什么有服务"这三个问题；事件先落盘再发送，断线重放。
03把工具收敛成一个命令行，并让帮助与权限同源。155 条命令听起来笨，但比 155 个 MCP server 可控得多；权限清单由代码生成，才不会文档与实现脱节。
04所有动作过同一道闸，且规则先于模型。便宜的规则先拦一层，贵的判断只看剩下的部分；每次输入先记日志再执行，不确定就不重放。
05把主动性做成有反馈回路的机制，并且把规则摊开给人看。规则可以被观察、被修改、被追溯——这一点比"我们很主动"重要得多。

也说三点保留

第一，许可证不是标准开源。它是"基于 Apache 2.0 加了附加条件"的 Linger Open Source License：禁止拿它做托管服务对外提供；前端 LOGO 和版权信息不得移除修改；并且贡献者同意版权方"可以按需调整开源协议"。商用自用可以，做 SaaS 不行。如果你的方案是"部署一套给别人用"，这条得先看清楚。

第二，"零 token 费"有边界。搜索、语音、应用连接这三块仍要外部服务或配置，硬件门槛也实打实。本地优先不等于断网可用。

第三，它还很新。四千星、380 fork、九个 release、141 个开放 issue——这是高速迭代的样子，也是"接口会变"的样子。我读的是 11 月 23 日的 main 分支，一个月后可能就不是这个样子了。

最后补一句关于我自己这篇的位置：我在这个系列里写过很多次"我的沙箱""我的记忆""我的驾驶舱"，每次都在解决同一类问题——一个能力不受控的东西，怎么放到可信的边界里。Linger 给出的答案是：把边界做在文件上（wiki 页面 + 变更日志）、做在网络姿态上（只出不进）、做在动作路径上（一道闸）、也做在规则上（Dreaming 的规则清单）。四个层面都做了，这可能是它二十天能涨四千星的原因之一。

结语：把不可能拆成一道排序题

回到开头那个矛盾：39 GB 的模型，怎么跑在 12 GB 的卡上？Linger 的答案是——不跑整个模型，只跑当前这个 token 需要的那几个专家，其余的按热度分层放远一点。

我一直觉得这个动作比它的技术细节更重要。它把一个看起来非黑即白的问题（装得下 / 装不下），变成了一个连续的排序问题（谁更热、谁放得近、换回来要多久）。工程上真正值钱的往往不是"做到了不可能的事"，而是"把不可能改写成了一个可以计算的取舍"。

这一点放在哪一行都成立。显存不够可以排序；上下文不够也可以排序；工具太多可以排序；连"什么时候该打扰用户"，它都做成了一张可以重写的规则清单——那也是一种排序：这件事，现在，值不值得占你一秒。
